# VFang v0.9.9 Arch-family support design

Date: 2026-08-08
Status: approved design

## Goal

Release VFang 0.9.9 with first-party Pacman packages and the same one-command,
pre-elevation verification flow already offered to DEB and RPM users.

The release directly supports current upstream Arch Linux and CachyOS on
`x86_64`. It also accepts other distributions that identify themselves as Arch
derivatives through `ID_LIKE=arch`, with the existing compatible-family warning
instead of claiming that every derivative was tested directly.

## User-visible result

The existing command remains the preferred installation path on every supported
distribution:

```sh
curl -fsSL https://github.com/bladeandsoulx/vfang-razer-linux/releases/latest/download/install.sh | bash
```

On an Arch-family system, the installer selects these exact v0.9.9 assets:

```text
fang-0.9.9-1-x86_64.pkg.tar.zst
fangd-0.9.9-1-x86_64.pkg.tar.zst
```

It validates their checksums and metadata, refuses downgrades, installs the pair
through Pacman, enables `fangd`, and reconciles membership in the `fang` group.
Users do not need an AUR helper, a local compiler, or a separately maintained
repository.

The release remains baseline `x86_64`. It does not add CachyOS-specific
`x86-64-v3`, `x86-64-v4`, or Zen builds because VFang supports Razer Blade
generations whose CPUs do not all implement those levels.

## Support boundary

### Directly supported

- Upstream Arch Linux with `ID=arch`.
- CachyOS with `ID=cachyos`, whether or not its `os-release` also supplies
  `ID_LIKE=arch`.

Both direct platforms receive clean-container package lifecycle coverage in the
pull-request, main-branch, and tag-release workflows. The Arch package is built
once and the identical pair is tested on both platforms.

### Compatible-family support

Any other distribution whose parsed `ID_LIKE` contains the exact token `arch`
uses the same Pacman package path and receives the warning:

```text
<Distribution> is compatible-family, not release-tested directly.
```

This includes conforming releases of distributions such as EndeavourOS,
Garuda, and Manjaro. Acceptance depends on the machine identifying its family
through `os-release`; VFang will not maintain an open-ended hardcoded list of
derivative names. A derivative that omits `ID_LIKE=arch` remains rejected unless
it is the explicit CachyOS direct-platform exception.

### Rolling-release contract

Arch-family systems do not have a stable base version that can be paired with a
codename in the same way as Ubuntu, Debian, or Fedora. VFang therefore gates the
Pacman family on the direct `ID` or the exact `arch` token in `ID_LIKE`, not on
`VERSION_ID`.

The supported state is a fully updated Arch-family installation. CI updates each
Arch and CachyOS test container before installing VFang. The release installer
does not silently update the operating system and never runs `pacman -Sy`, which
could create a partial-upgrade state. If Pacman cannot resolve the package
transaction, the installer preserves Pacman's diagnostic and advises the user
to run:

```sh
sudo pacman -Syu
```

and then retry VFang installation.

## Pacman package design

Add a focused `packaging/arch/` directory:

```text
packaging/arch/
├── PKGBUILD
├── build.sh
├── build-script.test.mjs
├── metadata.test.mjs
└── verify.sh
```

### Build boundary

`build.sh` owns compilation and reproducible artifact collection, following the
existing RPM packaging boundary:

1. Build `fangd` in release mode from the root Cargo workspace with locked
   dependencies.
2. Run `npm ci` for the app.
3. Build the Tauri desktop binary with no DEB/RPM bundler.
4. Stage the two binaries and existing packaging assets in a private temporary
   directory.
5. Invoke one split `PKGBUILD` as an unprivileged build user.
6. Copy exactly the two canonical package files into the requested output
   directory and reject missing, duplicate, or unexpected package output.

The split `PKGBUILD` packages both binaries without compiling them twice. Arch's
documented `package_fang()` and `package_fangd()` split-package functions keep
the payloads and dependency declarations independent while producing one
coherent release pair.

The Arch build runs in the upstream Arch container, not the CachyOS container.
This avoids inheriting CachyOS CPU-specific compiler defaults and preserves the
baseline `x86_64` contract. CachyOS tests the resulting upstream-Arch-built
artifacts rather than rebuilding them.

### `fangd` package

`fangd` installs:

- `/usr/bin/fangd`;
- `/usr/lib/systemd/system/fangd.service` from
  `packaging/fangd.service`;
- `/usr/lib/sysusers.d/fang.conf` from the existing sysusers declaration; and
- `/usr/share/licenses/fangd/LICENSE`.

Its runtime dependencies are `glibc`, `libgcc`, `systemd`, and `systemd-libs`.
`systemd-libs` supplies the linked `libudev.so.1`; `systemd` supplies the service
manager and Pacman sysusers hook. The package contains no custom `groupadd`
script. Installing the sysusers file lets the distribution's systemd Pacman
hook create the `fang` group declaratively.

The package version is `0.9.9-1`: application version `0.9.9`, package release
`1`, architecture `x86_64`, and license `GPL-2.0-only`.

### `fang` package

`fang` installs:

- `/usr/bin/fang`;
- `/usr/share/applications/fang.desktop`;
- 32, 128, 256, and 512-pixel icons in the corresponding hicolor directories;
  and
- `/usr/share/licenses/fang/LICENSE`.

The desktop package declares:

```text
fangd>=0.9.9
fangd<0.10.0
```

This preserves the same app/daemon compatibility line enforced by DEB and RPM
packages. Its native runtime dependency set is `cairo`, `dbus`, `gdk-pixbuf2`,
`glib2`, `glibc`, `gtk3`, `libgcc`, `libsoup3`, and `webkit2gtk-4.1`, plus
`libayatana-appindicator` for the dynamically loaded tray implementation and
`hicolor-icon-theme` for the installed icon layout. The Arch verification job
runs `namcap`, inspects the binary's direct ELF requirements, and fails on a
missing package dependency or unresolved shared library.

## Installer design

### Family classification

Extend platform classification to three package families: `deb`, `rpm`, and
`pacman`. Family markers are collapsed before conflict evaluation:

- Debian family: direct `ubuntu`/`debian`, or either token in `ID_LIKE`.
- RPM family: direct `fedora`, or `fedora` in `ID_LIKE`.
- Pacman family: direct `arch`/`cachyos`, or `arch` in `ID_LIKE`.

Ubuntu legitimately reports `ID=ubuntu` and `ID_LIKE=debian`; those are one DEB
family, not a conflict. An identity claiming markers from more than one package
family, such as `ID_LIKE="arch debian"`, fails before download or `sudo`.

Direct Arch and CachyOS matches do not require `VERSION_ID`. A derivative must
contain the exact whitespace-delimited `arch` token; substrings such as
`notarch` do not match.

### Canonical constants and manifest

Add these installer constants alongside the DEB and RPM constants:

```text
PACMAN_FANG=fang-${VERSION}-1-x86_64.pkg.tar.zst
PACMAN_FANGD=fangd-${VERSION}-1-x86_64.pkg.tar.zst
PACMAN_FANG_VERSION=${VERSION}-1
PACMAN_FANGD_VERSION=${VERSION}-1
```

The checksum manifest grows from five to seven canonical entries:

1. `install.sh`
2. desktop DEB
3. daemon DEB
4. desktop RPM
5. daemon RPM
6. desktop Pacman package
7. daemon Pacman package

The installer still downloads only `SHA256SUMS` and the selected package pair.
It rejects missing entries, duplicate entries, path components, noncanonical
filenames, unexpected assets, malformed digests, and extra lines.

### Metadata verification

Before elevation, extract only `.PKGINFO` with `bsdtar` and parse it as data.
Do not source it. Require one unambiguous value for each scalar identity field:

```text
pkgname = fang | fangd
pkgver = 0.9.9-1
arch = x86_64
```

For the desktop package, also require both exact daemon relations:

```text
depend = fangd>=0.9.9
depend = fangd<0.10.0
```

The parser rejects duplicate scalar fields, malformed lines, missing fields,
unexpected control characters, the wrong dependency range, or more than one
`.PKGINFO` archive member. Checksum verification happens before metadata
inspection, so metadata is parsed only from a release-authenticated package.

Pacman systems require `pacman`, `vercmp`, and `bsdtar` in addition to the
installer's common commands.

### Installed-state and transaction behavior

`pacman -Q -- fang` and `pacman -Q -- fangd` determine whether each package is
absent and return its installed full package version. The installer accepts
exactly one `name version` record and uses `vercmp` to classify that version as
older, equal, or newer than `0.9.9-1`.

The existing pair decision remains authoritative:

- either newer package aborts as a refused downgrade;
- two equal packages skip package installation;
- any absent or older member installs the complete pinned pair, repairing a
  partial installation and keeping the transaction coherent.

The mutating command is one transaction:

```sh
sudo pacman -U --noconfirm /tmp/.../fangd-0.9.9-1-x86_64.pkg.tar.zst \
  /tmp/.../fang-0.9.9-1-x86_64.pkg.tar.zst
```

Pacman installs required dependencies from the user's configured sync
repositories. The installer does not pass `--nodeps`, disable package signature
policy, refresh databases, or update unrelated packages. A failed transaction
aborts before service or group reconciliation.

After successful installation or a same-version no-op, the existing shared
logic verifies the `fang` group, enables and starts `fangd`, and adds the target
desktop user to the group if necessary.

## Release contract

VFang v0.9.9 expands the immutable release from six to exactly eight assets:

```text
install.sh
SHA256SUMS
Fang_0.9.9_amd64.deb
fangd_0.9.9-1_amd64.deb
fang-0.9.9-1.x86_64.rpm
fangd-0.9.9-1.x86_64.rpm
fang-0.9.9-1-x86_64.pkg.tar.zst
fangd-0.9.9-1-x86_64.pkg.tar.zst
```

`releaseNames()` and `checksumNames()` become the single inventory authority.
`stageRelease()` gains an explicit Arch artifact directory, validates exactly
two package files there, checks Pacman metadata with the same name/version/arch
rules as the installer, and copies the pair into the new private output
directory. Its command interface becomes:

```text
stage VERSION DEB_DIR RPM_DIR ARCH_DIR OUTPUT_DIR INSTALLER
```

The publisher names all eight uploads explicitly. Remote validation requires
the exact eight filenames, byte sizes, and SHA-256 digests before publishing the
draft. Existing immutable-release, never-clobber, and latest-release checks stay
unchanged.

## CI and release gates

### Static contract tests

The existing Ubuntu contracts job adds:

- Arch build-script tests;
- PKGBUILD metadata and payload-contract tests;
- installer Pacman-family fixtures and transaction states;
- release-stage and publisher eight-asset tests;
- version-sync tests for `pkgver` and dependency bounds; and
- ShellCheck coverage for `packaging/arch/build.sh` and
  `packaging/arch/verify.sh`.

### Arch build job

One `arch-build` job uses the official `archlinux:base-devel` container. It
fully updates the container, installs the declared build prerequisites, uses
the checked-in Rust and npm lockfiles, builds the pair with
`packaging/arch/build.sh`, asserts the canonical filenames, and uploads one
`fang-arch-packages` workflow artifact.

This job is the sole producer. Neither install-test job rebuilds packages.

### Install-test matrix

`arch-test` depends on `arch-build` and runs the same artifact in:

- `archlinux:base-devel`; and
- `cachyos/cachyos:latest`, the official CachyOS container.

Each matrix entry fully updates its rolling container before installing test
tools or VFang. It captures the parser-visible fields from that container's own
`/etc/os-release`, compares them with a checked-in projection under
`packaging/installer/os-release/`, and executes installer detection against the
real identity. This prevents a future CachyOS or Arch identity change from being
hidden by handwritten fixtures.

`packaging/arch/verify.sh` then checks:

1. Exactly two canonical package files exist.
2. Names, versions, releases, architecture, license, dependencies, and payload
   ownership are exact.
3. An incompatible dummy `fangd` cannot satisfy the desktop dependency range.
4. Pacman installs the local pair and resolves native dependencies.
5. `getent group fang` succeeds through the sysusers hook.
6. `pacman -Qkk fang fangd` reports no missing or altered packaged files.
7. `fangd --version` reports `0.9.9`.
8. The installed systemd unit passes `systemd-analyze verify`.
9. The existing daemon mock smoke test passes without hardware.
10. `ldd /usr/bin/fang` has no unresolved libraries.
11. The app remains alive for the bounded Xvfb and D-Bus smoke window.
12. Pacman removes both packages and every file owned by the packages is gone.

Containers do not prove real Razer hardware behavior or a complete KDE/Wayland
desktop session. Those remain manual hardware-test responsibilities.

### Release workflow

The tag workflow adds the Arch builder and Arch/CachyOS test matrix as publish
prerequisites:

```text
debs ──> deb-test ──────────────┐
rpms ──> rpm-test ──────────────┼─> publish eight assets
arch packages ──> arch-test ────┘
```

The publish job downloads all three package-family artifacts and stages the
exact eight-asset release only after every lifecycle gate passes.

## Versioning and documentation

`app/scripts/version.mjs check` adds the Arch `pkgver` and the desktop package's
lower/upper `fangd` dependency bounds to its synchronized version set.
`set 0.9.9` changes `pkgver` to `0.9.9`, resets/retains `pkgrel=1`, and updates
all existing Cargo, npm, Tauri, DEB, RPM, installer, banner, lockfile, and
changelog locations. Tests reject multiline or malformed PKGBUILD assignments
with the same fail-closed posture as RPM fields.

Documentation changes include:

- list Arch Linux and CachyOS as directly tested x86_64 platforms;
- explain that `ID_LIKE=arch` derivatives use compatible-family support;
- add the Pacman manual-install command and removal command;
- state that Arch-family users should fully update before installation;
- update the source-installer rejection copy to point Arch-family users to the
  released Pacman packages without adding an Arch source-build path;
- add Arch/CachyOS commands and evidence fields to `HARDWARE_TESTING.md`;
- add a v0.9.9 entry to `CHANGELOG.md` and the in-app changelog; and
- update documentation contract tests from v0.9.8/six assets to v0.9.9/eight
  assets without rewriting historical v0.9.4 release notes.

## Failure behavior

The following failures happen before any privileged operation:

- unsupported or conflicting distribution identity;
- unsupported CPU architecture;
- missing common or Pacman-specific commands;
- download failure or partial file;
- malformed, incomplete, duplicate, or expanded checksum manifest;
- checksum mismatch;
- malformed or incorrect `.PKGINFO` metadata;
- unexpected package names, versions, architecture, or dependency bounds; and
- either installed package being newer than v0.9.9-1.

After `sudo -v`, Pacman transaction failure stops the flow without attempting
service activation or user/group changes. Service and group reconciliation keep
their existing actionable diagnostics.

## Out of scope

- aarch64, i686, or architecture-specific optimized builds;
- an official Arch repository, CachyOS repository, AUR publication, or AUR
  helper integration;
- package signing beyond the existing HTTPS, pinned-release, and SHA-256
  release verification model;
- a Pacman branch in `packaging/install-from-source.sh`;
- direct lifecycle claims for every Arch derivative;
- automatic operating-system upgrades or repository refreshes;
- changing VFang hardware-control behavior; and
- changing DEB or RPM payloads except for shared version/release-contract
  synchronization required by v0.9.9.

## Acceptance criteria

VFang v0.9.9 is ready to tag only when:

- every version source reports `0.9.9` and every package release reports `1`;
- the release installer accepts direct Arch and CachyOS plus
  `ID_LIKE=arch` derivatives and rejects cross-family conflicts;
- checksum, metadata, upgrade, no-op, repair, and downgrade tests pass for the
  Pacman branch;
- the same two Arch-built package files pass full lifecycle verification on
  current Arch and CachyOS containers;
- DEB and RPM tests remain green;
- the staged and remotely validated release contains exactly eight assets and
  seven checksum entries; and
- README, hardware testing, changelog, in-app changelog, and their contract
  tests describe the same support boundary.
